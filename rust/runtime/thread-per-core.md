# Thread-per-core на Rust: пишем рантайм, в котором нет ни одного Mutex на горячем пути

В [прошлой статье](https://habr.com/ru/articles/1050160/) мы собрали async-рантайм с нуля: waker, executor, reactor. Получилась однопоточная штука, идейно похожая на smol. В самом конце там было одно предложение, которое я хочу развернуть:

> Glommio это thread-per-core поверх io_uring - другая архитектура, заслуживающая отдельного разбора.

Вот этот разбор. Мы напишем thread-per-core рантайм на чистом std (около 300 строк), построим на нём шардированное key-value хранилище и на цифрах увидим, где эта архитектура выигрывает у «tokio-style» в десятки раз, а где проигрывает ему же. Второе не менее важно, чем первое.

Весь код лежит в одном файле, `src/bin/tpc.rs`, и запускается через `cargo run --release --bin tpc`. Никаких зависимостей.

## Что не так с work-stealing

Напомню, как устроен tokio по умолчанию. Есть пул worker-потоков, есть глобальная очередь задач, и у каждого worker'а есть локальная. Когда worker'у нечего делать, он лезет в очередь соседа и «крадёт» оттуда задачу. Задача может начать выполняться на одном потоке, заснуть на `.await`, а проснуться на другом.

Отсюда следует три вещи.

**Первая: `tokio::spawn` требует `Send + 'static`.** Раз задача может переехать между потоками, всё, что она держит через `.await`, должно быть безопасно для переезда. `Rc` нельзя. `RefCell` нельзя. `MutexGuard` через `.await` нельзя. Это не придирка компилятора, это честное следствие архитектуры.

**Вторая: общее состояние живёт под `Arc<Mutex<..>>`.** Раз любой поток может выполнять любую задачу, любой поток может тронуть любые данные. Значит, данные надо защищать. Классический tokio-сервис выглядит как `Arc<Mutex<HashMap<..>>>` или `DashMap`, и каждый запрос делает `lock()`.

**Третья: кеши процессора работают против вас.** Когда восемь ядер по очереди берут один и тот же мьютекс, кеш-линия с этим мьютексом летает между ядрами. То же с самими данными. Ядро прогрело L1 под свою задачу, задачу украли, прогрев пропал.

Work-stealing решает важную проблему: балансировку нагрузки. Если одна задача тяжёлая, а остальные лёгкие, свободные потоки разберут лёгкие, и никто не простаивает. За это платят синхронизацией. Для большинства сервисов это правильная сделка. Но не для всех.

## Идея thread-per-core

Thread-per-core (TPC), она же shared-nothing, переворачивает подход. Вместо N потоков, которые делят одну очередь и одно состояние, у нас N полностью независимых рантаймов. У каждого свой executor, свой reactor, свои задачи и свой кусок данных. Задача, заспавненная на ядре 3, живёт и умирает на ядре 3.

Ядра общаются только сообщениями. Если ядру 1 нужны данные ядра 3, оно не берёт lock, оно отправляет запрос и ждёт ответ.

Так устроен Seastar, на котором написана ScyllaDB. В Rust так устроены три рантайма: glommio (DataDog), monoio (ByteDance) и compio. Так, с оговорками, работает Actix-web: у него отдельная `System` на каждый поток.

Раз задачи не переезжают, `Send` не нужен. Раз данные принадлежат ровно одному потоку, `Mutex` не нужен. Раз одно ядро всегда работает с одними и теми же данными, кеши прогреты. Звучит как бесплатный обед, и мы скоро увидим, где за него платят.

## Строим

### События ядра

Начнём с самого важного решения. В прошлой статье у executor'а была очередь готовых задач, а reactor жил в отдельном потоке и будил задачи через эту очередь. Здесь мы объединим всё в один канал на ядро. Через него приходят и «задача N готова», и «другое ядро просит тебя что-то сделать», и «выключайся».

```rust
type LocalFuture = Pin<Box<dyn Future<Output = ()>>>; // без Send

enum Event {
    Wake(usize),                    // задача с таким id готова к poll
    Run(Box<dyn FnOnce() + Send>),  // «выполни это у себя» от другого ядра
    Shutdown,
}
```

Обратите внимание на тип задачи: `dyn Future` без `Send`. Это и есть весь смысл. Замыкание в `Run`, наоборот, `Send`: оно пересекает границу потоков.

### Waker

В прошлой статье мы собирали `RawWakerVTable` руками. Это полезно, чтобы понять механику, но в реальном коде стоит взять `std::task::Wake`. Он делает то же самое, только за `Arc` следит компилятор.

```rust
struct TaskWaker {
    id: usize,
    tx: Sender<Event>,
}

impl Wake for TaskWaker {
    fn wake(self: Arc<Self>) {
        self.wake_by_ref();
    }
    fn wake_by_ref(self: &Arc<Self>) {
        let _ = self.tx.send(Event::Wake(self.id));
    }
}
```

Важная деталь: `Waker` обязан быть `Send + Sync`, даже в TPC. Задача не переезжает между ядрами, но разбудить её могут откуда угодно. Когда ядро 3 отвечает на запрос ядра 1, оно дёргает waker задачи, которая живёт на ядре 1. Через `Sender` это безопасно.

### Handle

Снаружи ядро выглядит как один метод: «выполни у себя это замыкание».

```rust
#[derive(Clone)]
struct Handle {
    tx: Sender<Event>,
}

impl Handle {
    fn run(&self, f: impl FnOnce() + Send + 'static) {
        let _ = self.tx.send(Event::Run(Box::new(f)));
    }
}
```

Это единственная дверь в ядро. Заспавнить задачу на чужом ядре напрямую нельзя, но можно попросить ядро заспавнить её самому. Замыкание должно быть `Send`, а вот задача, которую оно создаст внутри, уже нет.

### Thread-local контекст

Каждое ядро держит в `thread_local!` свой контекст: номер, канал, таймеры и очередь на spawn.

```rust
#[derive(Clone)]
struct CoreCtx {
    id: usize,
    tx: Sender<Event>,
    timers: Rc<RefCell<Timers>>,
    spawn_q: Rc<RefCell<Vec<LocalFuture>>>,
}

thread_local! {
    static CURRENT: RefCell<Option<CoreCtx>> = const { RefCell::new(None) };
}

fn spawn_local(f: impl Future<Output = ()> + 'static) {
    with_ctx(|c| c.spawn_q.borrow_mut().push(Box::pin(f)));
}
```

Всё в `Rc`, и это не лень, а гарантия: из другого потока сюда не добраться в принципе. `spawn_local` не требует `Send`, и это главное отличие API от `tokio::spawn`. Очередь на spawn нужна, потому что задача может заспавнить другую задачу прямо во время своего `poll`, когда `HashMap` с задачами уже занят.

### Ядро: executor и reactor в одном цикле

В прошлой статье reactor был отдельным потоком, который крутился в цикле с `sleep(1ms)` и будил задачи. В TPC так не делают. Reactor и executor живут в одном цикле, и когда задач нет, поток честно засыпает до ближайшего таймера или до внешнего события.

```rust
fn run(mut self) {
    loop {
        // reactor: ждём событие, но не дольше ближайшего таймера
        let next_deadline = self.ctx.timers.borrow().map.keys().next().map(|k| k.0);
        let first = match next_deadline {
            Some(deadline) => {
                let timeout = deadline.saturating_duration_since(Instant::now());
                match self.rx.recv_timeout(timeout) {
                    Ok(ev) => Some(ev),
                    Err(RecvTimeoutError::Timeout) => None,
                    Err(RecvTimeoutError::Disconnected) => return,
                }
            }
            None => match self.rx.recv() {
                Ok(ev) => Some(ev),
                Err(_) => return,
            },
        };

        // забираем всё, что уже накопилось, одной пачкой
        let mut batch: Vec<Event> = first.into_iter().collect();
        while let Ok(ev) = self.rx.try_recv() {
            batch.push(ev);
        }

        // executor
        for ev in batch {
            match ev {
                Event::Wake(id) => self.poll_task(id),
                Event::Run(f) => f(),
                Event::Shutdown => return,
            }
        }

        // истёкшие таймеры будят свои задачи через тот же канал
        let now = Instant::now();
        let mut timers = self.ctx.timers.borrow_mut();
        while let Some(entry) = timers.map.first_entry() {
            if entry.key().0 > now { break; }
            entry.remove().wake();
        }
        drop(timers);

        // новые задачи, заспавненные во время poll
        let new: Vec<LocalFuture> = self.ctx.spawn_q.borrow_mut().drain(..).collect();
        for fut in new {
            let id = self.next_id;
            self.next_id += 1;
            self.tasks.insert(id, fut);
            let _ = self.ctx.tx.send(Event::Wake(id));
        }
    }
}
```

Здесь `recv_timeout` играет роль `epoll_wait` с таймаутом. В настоящем рантайме на этом месте стоит `epoll_wait`, `kqueue` или `io_uring_enter`, а канал событий и сетевые дескрипторы мультиплексируются в одном вызове. Но структура цикла ровно такая: подождать, обработать пачку, обслужить таймеры, повторить.

Таймеры лежат в `BTreeMap<(Instant, u64), Waker>`. Ближайший всегда первый, и нам не нужен линейный перебор, как в прошлой статье. Tokio использует иерархическое колесо таймеров, но для понимания архитектуры `BTreeMap` достаточно.

`poll_task` не изменился по сравнению с прошлой статьёй, разве что waker теперь создаётся через `Waker::from(Arc::new(TaskWaker { .. }))`.

### Таймер без фонового потока

```rust
impl Future for Sleep {
    type Output = ();
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        if Instant::now() >= self.when {
            return Poll::Ready(());
        }
        if !self.registered {
            self.registered = true;
            let when = self.when;
            let waker = cx.waker().clone();
            with_ctx(|c| {
                let mut t = c.timers.borrow_mut();
                t.seq += 1;
                let seq = t.seq;
                t.map.insert((when, seq), waker);
            });
        }
        Poll::Pending
    }
}
```

Таймер регистрируется в reactor'е своего ядра через thread-local. Ни `Arc`, ни канала в фоновый поток. Порядковый номер `seq` нужен, чтобы два таймера на один и тот же `Instant` не затёрли друг друга в `BTreeMap`.

### Oneshot: единственный Mutex

Когда ядро 1 просит ядро 3 что-то сделать, ему нужно дождаться ответа. Для этого нужен канал на одно сообщение, и он по определению пересекает границу потоков. Здесь `Mutex` неизбежен.

```rust
struct Slot<T> {
    value: Option<T>,
    waker: Option<Waker>,
}

impl<T> OneshotTx<T> {
    fn send(self, v: T) {
        let mut g = self.0.lock().unwrap();
        g.value = Some(v);
        let waker = g.waker.take();
        drop(g);
        if let Some(w) = waker {
            w.wake(); // разбудить задачу на другом ядре
        }
    }
}

impl<T> Future for OneshotRx<T> {
    type Output = T;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<T> {
        let mut g = self.0.lock().unwrap();
        match g.value.take() {
            Some(v) => Poll::Ready(v),
            None => {
                g.waker = Some(cx.waker().clone());
                Poll::Pending
            }
        }
    }
}
```

Разница с tokio не в том, что мьютексов нет вообще. Разница в том, где они стоят. В tokio-сервисе мьютекс защищает данные, и его берут на каждой операции. Здесь мьютекс стоит на границе между ядрами, а данные внутри ядра не защищены ничем, потому что не от кого.

Заметьте: `send` сначала отпускает lock, потом зовёт `wake`. Иначе, если waker синхронно попробует что-то сделать с тем же слотом, будет deadlock. Это общий принцип: никогда не держите lock, когда дёргаете чужой код.

### Шардированное хранилище

Теперь самое интересное. Каждое ядро владеет своим куском ключевого пространства, и шард живёт в обычном `HashMap` внутри `thread_local!`.

```rust
thread_local! {
    static SHARD: RefCell<HashMap<u64, u64>> = RefCell::new(HashMap::new());
}

impl Cluster {
    fn owner(&self, key: u64) -> usize {
        (key % self.cores.len() as u64) as usize
    }

    async fn put(&self, key: u64, val: u64) -> Option<u64> {
        let owner = self.owner(key);
        if owner == core_id() {
            // быстрый путь: ключ наш, никакой синхронизации
            return SHARD.with(|s| s.borrow_mut().insert(key, val));
        }
        // медленный путь: просим владельца и ждём ответ
        let (tx, rx) = oneshot();
        self.cores[owner].run(move || {
            let old = SHARD.with(|s| s.borrow_mut().insert(key, val));
            tx.send(old);
        });
        rx.await
    }
}
```

Быстрый путь: одна проверка и обращение к `HashMap`. Ни атомиков, ни lock. Медленный путь: аллокация замыкания, отправка через канал, пробуждение чужого потока, lock на oneshot, обратное пробуждение. Разница между ними, как мы сейчас увидим, примерно в 50 раз.

## Демо

Первая задача держит `Rc<RefCell<Vec<String>>>` через `.await`. В `tokio::spawn` это не скомпилируется.

```rust
cluster.cores[0].run(move || {
    let log: Rc<RefCell<Vec<String>>> = Rc::default();
    for i in 0..3 {
        let log = log.clone();
        spawn_local(async move {
            sleep(Duration::from_millis(10 * (3 - i))).await;
            log.borrow_mut().push(format!("task {i} on core {}", core_id()));
        });
    }
    // ...
});
```

Вторая задача с ядра 1 пишет ключ 42, которым владеет ядро 2, и читает его обратно.

```
--- demo on 8 cores ---
core 1: key 42 lives on core 2, get -> Some(7)
core 0 log: ["task 2 on core 0", "task 1 on core 0", "task 0 on core 0"]
```

Таймеры отработали в правильном порядке, `Rc` пережил три `.await`, кросс-ядерный запрос вернулся с ответом.

## Бенчмарк

Нагрузка одинаковая во всех вариантах: 8 ядер, на каждом 32 задачи, каждая делает 20 000 операций, чередуя `put` и `get`. Ключевое пространство 65 536 ключей.

Вариант A: один `HashMap` под `Arc<Mutex<..>>`, все восемь потоков берут lock на каждую операцию. Это «tokio-style» общее состояние.

Варианты B: шарды. Меняется только доля операций, которые попадают на своё ядро. 100% локальных ключей означает shard-aware клиента, который знает, куда слать запрос. 12% (то есть 1/8) означает, что ключи случайные и клиент ничего не знает.

Apple M-серия, 8 ядер, `--release`. Колонка ns/op считается по wall-clock на все ядра вместе, то есть это обратная пропускная способность.

| Вариант | Время | Пропускная способность | ns/op (wall) |
|---|---|---|---|
| shared `Arc<Mutex<HashMap>>` | 402 ms | 12.7 Mops/s | 79 |
| sharded, 100% локальных ключей | 9 ms | 541 Mops/s | 2 |
| sharded, 90% локальных ключей | 93 ms | 55 Mops/s | 18 |
| sharded, 50% локальных ключей | 448 ms | 11.4 Mops/s | 87 |
| sharded, 12% локальных ключей (случайные) | 739 ms | 6.9 Mops/s | 144 |

Три вывода.

**При полной локальности TPC быстрее мьютекса в 40 раз.** И это не потому, что мьютекс медленный. 79 ns на операцию при восьми конкурирующих потоках это хороший результат для мьютекса. Просто локальный `HashMap` без синхронизации делает операцию за 20 ns на ядро, а восемь ядер масштабируются линейно, потому что им нечего делить.

**При случайных ключах TPC проигрывает мьютексу почти вдвое.** Каждая удалённая операция стоит примерно микросекунду: аллокация `Box<dyn FnOnce>`, `send` в канал, пробуждение потока из `recv_timeout`, lock на oneshot, обратное пробуждение. Мьютекс за это время успевает обслужить десяток запросов.

**Точка безубыточности где-то около 50% локальности.** Ниже этого порога мьютекс выигрывает.

Это и есть главное, что нужно понимать про thread-per-core. Архитектура не «быстрее tokio». Она быстрее ровно тогда, когда запрос попадает на нужное ядро сразу, и медленнее, когда не попадает. Поэтому все системы вокруг Seastar построены так, чтобы локальность была высокой:

- ScyllaDB отдаёт клиенту карту шардов, и shard-aware драйвер отправляет запрос сразу в правильное TCP-соединение, привязанное к правильному ядру.
- Сетевые серверы на TPC слушают один порт с `SO_REUSEPORT`, и ядро ОС само раскидывает соединения по потокам. Всё состояние соединения живёт на том ядре, которое его приняло.
- Когда кросс-ядерных запросов не избежать, их батчат: не одно сообщение на операцию, а пачка.

Если в вашей задаче данные нельзя разбить на независимые куски, TPC вам не поможет, а помешает.

## От игрушки к glommio, monoio и compio

Наш рантайм показывает архитектуру, но до настоящего ему далеко. Три реальных thread-per-core рантайма на Rust добавляют примерно одно и то же, и различаются в основном платформами.

| | glommio | monoio | compio |
|---|---|---|---|
| Кто | DataDog | ByteDance | сообщество |
| Linux | io_uring | io_uring, fallback на epoll | io_uring, fallback на polling |
| macOS | нет | kqueue | polling |
| Windows | нет | экспериментально | IOCP |
| `spawn` без `Send` | да | да | да |
| Очереди с приоритетами, pinning | да | нет | нет |

Compio самый переносимый из трёх, glommio самый близкий к Seastar. Все трое строятся на completion-based вводе-выводе: буфер отдаётся ядру ОС заранее, а обратно приходит не «сокет готов», а «прочитано N байт». Поэтому их `read` и `write` забирают буфер по значению и возвращают его вместе с результатом. Это заметно отличается от API tokio и smol, где reactor сообщает о готовности, а читаете вы сами. Из-за этого ни один из трёх не построен поверх tokio: mio не даёт управлять io_uring и IOCP напрямую.

Вот что добавляют они и чего не хватает нам.

**io_uring на каждом ядре.** У каждого потока свои submission и completion кольца. Отправка запроса на чтение это запись в кольцо в памяти, без syscall. Reactor вместо `recv_timeout` ждёт на `io_uring_enter`, и там же приходят и сетевые события, и таймеры, и сообщения от соседей. Это работает только на Linux, поэтому в статье его нет, а наш код запускается на macOS. Если хочется thread-per-core на macOS или Windows, берите compio.

**Привязка к физическим ядрам.** `sched_setaffinity` на Linux гарантирует, что поток `core-3` всегда работает на CPU 3, и его L1/L2 никто не вытесняет. На macOS такого API нет, и планировщик ОС может перекинуть поток. Без привязки часть выигрыша от кешей теряется.

**Аллокатор на ядро.** Если аллокатор глобальный, `Box::new` внутри «локального» кода всё равно берёт lock или атомик. Seastar использует свой аллокатор, где у каждого шарда своя арена.

**Каналы между ядрами без Mutex.** Наш `Event::Run` идёт через `std::sync::mpsc`, а oneshot через `Mutex`. Glommio использует lock-free SPSC-очереди между каждой парой ядер, и стоимость кросс-ядерного сообщения падает до сотен наносекунд. Но не до нуля.

**Кооперативная вытесняемость.** В TPC одна задача, которая крутит тяжёлый цикл без `.await`, останавливает всё ядро целиком, включая сетевой ввод-вывод. Work-stealing это переживёт, остальные потоки разберут нагрузку. Glommio даёт `yield_if_needed()` и разные очереди с приоритетами, monoio и compio ограничиваются обычным `yield_now`, но во всех трёх ответственность за то, чтобы не блокировать ядро, лежит на программисте.

**Балансировка.** Если один шард горячий, а остальные простаивают, TPC ничего не может с этим сделать. Work-stealing может. Это фундаментальная цена shared-nothing, и решается она только на уровне схемы данных.

## Можно ли так на tokio?

Можно, и это стоит знать. `tokio::runtime::Builder::new_current_thread()` создаёт однопоточный рантайм, а `tokio::task::LocalSet` даёт `spawn_local` без `Send`. Если поднять по такому рантайму на каждом потоке и общаться через `tokio::sync::mpsc`, получится примерно то же, что мы написали. Именно так устроен Actix-web.

Разница с glommio будет в reactor'е: tokio использует epoll через mio, а не io_uring, и в аллокаторе, и в межъядерных очередях. Но архитектурно это тот же thread-per-core.

## Итоги

Thread-per-core это не оптимизация, это другая модель. Она меняет три вещи:

1. Задачи не переезжают между потоками, поэтому `Send` не нужен, и `Rc<RefCell<..>>` живёт через `.await`.
2. Данные принадлежат ровно одному потоку, поэтому на горячем пути нет `Mutex`, а кеши прогреты.
3. Ядра общаются сообщениями, и каждое сообщение стоит примерно микросекунду.

Из третьего пункта следует всё остальное. Если ваши данные шардируются и клиент может попасть на нужный шард, вы получаете линейное масштабирование и в разы большую пропускную способность. Если нет, вы получаете систему, которая медленнее обычного мьютекса и сложнее в написании.

Исходники всех трёх рантаймов читаются после этой статьи так же хорошо, как smol после прошлой. У glommio начните с `src/sys/uring.rs` и `src/executor/mod.rs`. У compio самый компактный код: `compio-runtime` это буквально наш `Core`, а `compio-driver` это его reactor с тремя бэкендами за одним трейтом, и по нему хорошо видно, чем io_uring, IOCP и polling отличаются друг от друга. Seastar на C++ тяжелее, но его [туториал](https://github.com/scylladb/seastar/blob/master/doc/tutorial.md) объясняет shared-nothing лучше любой другой документации. И, если хочется совсем глубоко, статья «The Impact of Thread-Per-Core Architecture on Application Tail Latency» (Enberg, Rao, Tarkoma, 2019) показывает, где TPC выигрывает по хвостовым задержкам, а не только по пропускной способности.
